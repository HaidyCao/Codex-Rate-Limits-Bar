## 对齐规则

- 两份历史出现相同的后续记录时，对齐上一个共同记录至该汇合点之间的累计样本，按已确认的前驱重新计算增量。例如 `[100, 300]` 与 `[200, 300]` 合计为 300。
- 没有后续汇合证据的尾部继续分别计数。例如 `[100, 200]` 与 `[100, 250]` 合计为 350。后续新增汇合记录可能修正此前的合计。
- 日统计对齐全部选定来源；周统计单独对齐当前账户来源，防止其他 home 的更细样本扣掉当前账户的已知用量。
- 对齐使用跨日的前置样本，再按事件时间归入统计范围。费用沿用该事件的模型、模式和请求上下文；无法确认的 token 明细继续保持未计价。
- 文件头跳过空行后读取会话信息，仍限制单条记录大小，并响应扫描取消。
- 累计顺序与时间顺序矛盾时保留可观察的贡献并报告对齐不完整，状态跨重启保留，日志修复后重算；其他来源的冲突不会污染干净的周统计。

## 实施步骤

1. 添加互补历史、汇合后再次分叉、多组部分共享、跨日、跨 home、文件头空行的独立期望值回归。
2. 将副本历史对齐放在临时内存中；落盘仍保存精简合计。使用副本算法版本使旧副本缓存重算，保留周观察基线和样本，避免重扫无关的正常单文件。
3. 比较首次读取、增量、重启、完整重建和文件顺序变换；保留现有 fork、回退、归档移动、失败恢复及计价完整性测试。
4. 运行 `make verify` 和 `make benchmark`，补充大量副本样本的性能检查，再备份状态、安装并验证实际读取。

缓存文档仍为 v4，新增可选的副本算法版本和冲突状态。旧副本缓存自动重放；旧缓存中曾被算作 JSON 错误的空白行也会重新检查。正常、未变化的单文件可直接复用旧缓存，周观察的起点、账户和官方样本不重置。

副本压力测试还定位了逐记录构造日期解析器的开销。解析器现由各扫描器独立持有，并在扫描锁内复用；汇总直接使用已解析的时间。2 万个累计样本、8 个副本的冷扫描由约 39.07 秒降至 8.56 秒，重建由约 38.82 秒降至 9.52 秒，无变化读取约 0.0033 秒；缓存约 23 KB，增量、重启和重建结果一致。标准 256 MiB 流式样例冷扫约 1.87 秒、重建约 1.73 秒，两个性能样例均满足缓存和内存限制。
